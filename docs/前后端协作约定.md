# ADC 牙科连锁诊所运营管理系统 · 前后端协作约定

版本：v2.2（2026-11-26）

本文件是前端和后端共同遵守的约定。前端（网页和微信小程序）和后端分开开发，**只靠本文件对齐**。网页和小程序调用的是**同一套后端接口**。任何一方想改接口，先改本文件并在末尾“变更记录”登记，再改代码。

系统分两端：**员工端**（网页后台，前台、牙医、总部使用，第 9.1—9.14 节）和**患者端**（官网与微信小程序，患者注册登录后提交预约申请，第 9.15—9.17 节），共用同一个后端。

需求来源：课程报告《ADC系统分析与设计完整报告》第五、六章（13 个系统用例及规约）、第十章（数据库）、第十一章（业务规则）、第十二章（界面）。本文件把其中与接口有关的部分落成具体格式；业务规则以报告为准，本文件只在报告没说清的地方补充。

**怎么读**：第 1—8 节是通用约定，两边都必须遵守；第 9 节按用例列出每个接口，写某个模块时只看对应小节加第 1—8 节即可；第 10—12 节是操作记录、示例数据和联调步骤；第 14 节是中文业务名和字段名对照。

## 1. 分工

| | 前端 | 后端 |
|---|---|---|
| 技术 | 网页：Vue 3 + Vite + Element Plus + Vue Router + axios；小程序：微信小程序 | Spring Boot（Java 17）+ Spring Data JPA + Spring Security + MySQL 8 + Flyway |
| 工程目录 | 网页 `E:\adc-system\frontend`；小程序 `E:\adc-system\miniprogram` | `E:\adc-system\backend` |
| 负责 | 页面、表单、输入格式检查、调用接口、展示结果和错误 | 数据库、全部业务规则和计算、权限、事务、并发与重复提交保护 |
| 不负责 | 不计算权威金额，不判断业务能否办理（只做提示） | 不写页面 |

原则：**规则只在后端执行一次**。前端可以提前提示（比如必填项），但后端必须自己再检查一遍；金额、状态、权限一律以后端返回为准。

## 2. 运行与连接

| 项目 | 约定 |
|---|---|
| 后端端口 | `8080` |
| 前端开发端口 | `5173`（`npm run dev`） |
| 接口前缀 | 所有接口都以 `/api` 开头 |
| 开发时连接 | 网页开发服务器把 `/api` 转发到 `http://localhost:8080`，浏览器看来是同一个地址，后端**不需要**配置跨域（CORS） |
| 部署时连接 | Nginx 提供网页打包文件，并把 `/api` 转发到后端 8080；同样是同一个地址 |
| 小程序连接 | 小程序直接请求服务器地址（如 `http://服务器IP/api/...`），不受跨域限制；演示时在微信开发者工具里勾选“不校验合法域名” |
| 数据库 | MySQL 8，库名 `adc`，字符集 `utf8mb4`；连接密码放在后端本地配置文件里，不提交 |

前端在后端没写好之前使用**模拟数据**开发（前端自己的开关 `VITE_USE_MOCK=true`）。后端某个接口写好后，前端关掉模拟就直接连真接口，所以**两边的路径和字段名必须和本文件一字不差**。

## 3. 数据格式

| 类型 | 格式 | 例子 |
|---|---|---|
| 请求与响应 | JSON，UTF-8 | |
| 字段命名 | 英文小驼峰 | `scheduledAt`、`accountNo` |
| 编号 | 数字 | `"id": 12` |
| 日期 | `YYYY-MM-DD` | `"2026-11-20"` |
| 日期时间 | `YYYY-MM-DDTHH:mm:ss`，本地时间，不带时区 | `"2026-11-20T09:30:00"` |
| 金额 | 数字，单位元，后端保证两位小数 | `"unitPrice": 80.00` |
| 数量 | 数字，最多 6 位小数 | `"quantity": 0.5` |
| 可空字段 | 返回 `null`，不要省略字段 | `"email": null` |
| 布尔 | `true` / `false` | |

后端用 `LocalDate`、`LocalDateTime`、`BigDecimal`。Jackson 需关闭“日期写成时间戳”。

**时区**：所有时间都是北京时间。后端取“当前时间”一律按 `Asia/Shanghai`（JVM 启动参数或配置里明确指定），因为云服务器默认常是 UTC，不指定会差 8 小时。

**查询参数**：日期范围统一用 `from`、`to`（`YYYY-MM-DD`，两端都包含）；多个编号用英文逗号分隔，如 `clinicIds=1,2`。

## 4. 登录与权限

用**令牌（Token）**，不用 Session + Cookie，因为微信小程序不会自动携带 Cookie，网页和小程序要共用同一套登录。

| 接口 | 说明 |
|---|---|
| `POST /api/auth/login` | 请求 `{"username":"front1","password":"..."}`；成功返回 `{ "token":"...", "expiresAt":"2026-11-20T21:30:00", "user":当前用户 }`；用户名或密码错误返回 401（`message`：“用户名或密码错误”），账号停用返回 401（`message`：“账号已停用，请联系总部”，与第 9.13 节一致） |
| `GET /api/auth/me` | 返回当前用户；令牌无效或过期返回 401 |
| `POST /api/auth/logout` | 退出，返回 200；后端**立即作废**本次请求携带的令牌，之后再用它访问任何接口都返回 401。前端无论收到 200 还是 401 `UNAUTHENTICATED`（例如网络超时后重试退出，令牌已被作废），都清除本地令牌并回到登录页 |

除登录接口外，所有请求在请求头带：

```
Authorization: Bearer <token>
```

当前用户格式：

```json
{ "id": 1, "username": "front1", "displayName": "王丽", "role": "FRONT_DESK", "dentistId": null }
```

令牌要求：后端可用 JWT，也可用服务端保存的随机字符串，前端不关心内部格式；有效期 **12 小时**；Spring Security 设为无状态（不创建 Session）。因为退出要立即作废令牌，若用 JWT，后端需记录已作废的令牌（至少保留到其过期时间）。

岗位 `role` 只有三种：`FRONT_DESK`（前台）、`DENTIST`（牙医，`dentistId` 有值）、`HQ`（总部）。

**患者账号**（官网和小程序使用，见第 9.16 节）与员工账号分开存放、分开登录：患者用 `POST /api/patient-auth/login` 取得令牌，同样放在 `Authorization: Bearer` 请求头里。患者令牌只能访问 `/api/patient/**` 和第 9.16 节中标“患”的接口，访问员工接口 → 403；员工令牌访问 `/api/patient/**` → 403。第 9.15 节的公开接口和第 9.16 节的注册、登录、验证码、找回密码不需要令牌。

要求：
- 没带令牌、令牌无效或过期，访问任何 `/api/**`（登录接口和第 9.15、9.16 节免登录的接口除外）→ 返回 **401 + JSON**，不要重定向到登录页。
- 已登录但岗位不对 → 返回 **403 + JSON**。
- 关闭 CSRF（使用请求头令牌，不依赖 Cookie）。
- 演示阶段为方便小程序调试，后端允许任意来源跨域访问 `/api/**`（允许 `Authorization`、`Content-Type`、`X-Request-Id` 请求头）；网页本身同源，不受影响。
- 每个接口允许的岗位见第 9 节各表的“岗位”列。三种岗位都能看全部诊所的数据（报告重点是跨诊所）。

演示账号由后端在示例数据里建好（密码统一为 `123456`，仅用于课程演示）：

| `dentist1` | 牙医（绑定员工编号 D001） | 林嘉文 |

## 5. 成功与错误

**成功**：HTTP 200（新建用 201 也可以），响应体直接是数据，不要再包一层 `{code, data}`。

**失败**：用 HTTP 状态码区分大类，响应体统一为：

```json
{
  "code": "STATE_NOT_ALLOWED",
  "message": "该预约已登记到诊，不能按普通预约取消",
  "fieldErrors": [ { "field": "phone", "message": "电话不能为空" } ],
  "current": null
}
```

- `message`：直接给用户看的中文说明，前端原样显示。
- `fieldErrors`：只有输入校验失败时有值，`field` 用请求里的字段名；其他情况为 `null`。
- `current`：`CHANGED` 时放对象的最新内容，结构与该对象详情 GET 的响应完全相同，前端用它刷新后让用户重新核对；患者新建疑似重复（409 `CONFLICT`）时放候选患者摘要数组；其他情况（包括其他重名冲突）为 `null`。

| HTTP | code | 含义（对应报告 11.2 的失败分类） |
|---|---|---|
| 400 | `INVALID_INPUT` | 输入缺失或不合法 |
| 401 | `UNAUTHENTICATED` | 未登录，或令牌无效、过期 |
| 403 | `FORBIDDEN` | 岗位无权办理 |
| 404 | `NOT_FOUND` | 对象不存在 |
| 409 | `STATE_NOT_ALLOWED` | 当前状态不允许，例如已到诊的预约不能取消 |
| 409 | `CHANGED` | 记录已被别人修改，或预览后依据已变化，需重新核对 |
| 409 | `CONFLICT` | 违反唯一规则，例如同一牙医同一时间已有预约、项目同日已有价格 |
| 409 | `DUPLICATE_REQUEST` | 同一请求标识被用于不同内容 |
| 500 | `INTERNAL` | 其他错误；`message` 写“系统错误，请稍后重试”，不要把异常堆栈给前端 |

## 6. 修改、确认与重复提交

报告第十一章要求“预览不写库、确认时复核、重复提交不产生重复记录”。统一做法：

1. **版本号**：可编辑的对象（诊所、牙医、治疗项目、患者、预约、就诊）响应里都带 `version`（数字）。前端修改时原样带回；后端用 JPA `@Version` 比对，不一致返回 409 `CHANGED`，`current` 放最新内容。
2. **预览—确认两步**（只用于诊疗确认、开结算单、季度核算）：预览接口只计算不写库，返回 `checkToken`（后端对所依据的数据算出的摘要字符串）；确认接口带回 `checkToken`，后端重新计算，不一致就返回 409 `CHANGED`。
3. **请求标识**：除 `POST /api/auth/login`、`POST /api/auth/logout`、第 9.16 节 `/api/patient-auth/**` 的全部接口和“只算不写”的接口（`check`、`price-lines`、`settlement-preview`、`preview`）外，所有 `POST`、`PUT` 请求，前端都在请求头带 `X-Request-Id`（每次用户点确认时新生成的 UUID；网络超时重试时沿用同一个）。后端记录处理过的请求：
   - 同一标识、同样内容再次到达 → 返回第一次的结果，不再写库；
   - 同一标识、不同内容 → 409 `DUPLICATE_REQUEST`。
   - 患者端的 `POST` 同样带请求标识。员工账号和患者账号的编号可能相同，后端记录请求时要能区分是哪一类账号。

## 7. 状态值

状态由后端根据字段算出来后放在响应里，前端只负责显示。

**预约 `status`**

| 值 | 显示 | 判定 |
|---|---|---|
| `VALID` | 有效 | 未取消、未到诊、预约时间未过 |
| `PENDING_VERIFY` | 待核实 | 未取消、未到诊、预约时间已过（不等于取消） |
| `CANCELLED` | 已取消 | 取消时间有值 |
| `ARRIVED` | 已到诊 | 到诊标记为真 |

**就诊 `status`**

| 值 | 显示 | 判定 |
|---|---|---|
| `UNCONFIRMED` | 诊疗未确认 | 诊疗确认时间为空 |
| `CONFIRMED` | 已确认待结算 | 已确认、有实际治疗、无结算单 |
| `SETTLED` | 已结算 | 有结算单 |
| `NO_TREATMENT` | 未实施治疗结束 | 已确认、未实施治疗原因有值、无实际治疗（新增规则） |

**预约申请 `status`**（第 9.17 节）

| 值 | 显示 | 判定 |
|---|---|---|
| `PENDING` | 待确认 | 患者已提交，前台尚未处理 |
| `CONFIRMED` | 已确认 | 前台已转为正式预约（`appointment` 有值） |
| `INVALID` | 无效 | 前台判定无效并填写原因 |
| `WITHDRAWN` | 已撤回 | 患者在前台处理前自己撤回 |

**期望时段 `timeSlot`**：`MORNING`（上午 09:00—12:00）/ `AFTERNOON`（下午 14:00—17:00）/ `EVENING`（傍晚 17:00—20:00）。

**季度核算 `fundStatus`**：`ACCRUED`（已计提激励基金，公司净利润 > 0）/ `TRANSFERRED`（基金已转总部处理，公司净利润 ≤ 0）。

## 8. 业务计算口径（后端实现，前端只显示）

- 每行小计 = 四舍五入(单位数量 × 当次单价, 2 位)，**中点远离零**（Java `RoundingMode.HALF_UP`），不能用浮点数；总额 = 各行已舍入小计之和。
- 实际治疗的单价按**实际到诊日期**取该项目“适用起始日期 ≤ 到诊日期”的最近一条标准价格，保存为快照，以后调价不改。
- 取消率 = 预约日期在统计期内的患者取消数 ÷ 该期预约总数；分母含已取消的；分母为 0 时 `rate` 为 `null`（显示“不适用”）；待核实不计入取消。
- 牙医净利润 = 收入 − 医疗用品成本 − 运营费用；公司净利润 = 各牙医净利润之和；公司净利润 > 0 时激励基金 = 公司净利润 × 10%（舍入到分），否则激励基金为 `null`，必须填写基金处理说明。
- 季度收入按**实际到诊日期**归季度、按**实际接诊牙医**归属，只算已开结算单的就诊。
- 汇总周期（愿景指标）= 从季度结束次日起到该季度**首次**确认时间的工作日数（周一至周五，暂不扣法定节假日）。

## 9. 接口清单

岗位缩写：前 = FRONT_DESK，医 = DENTIST，总 = HQ，全 = 三种都可。

### 9.1 下拉选项（全）

| 方法和路径 | 说明 |
|---|---|
| `GET /api/options/clinics?activeOnly=true` | `[{ "id":1, "name":"天河诊所", "active":true }]` |
| `GET /api/options/dentists?activeOnly=true` | `[{ "id":1, "employeeNo":"D001", "name":"林嘉文", "active":true, "verifiedQualifications":["口腔全科"] }]` |

### 9.2 UC08 维护诊所资料（总）

| 方法和路径 | 请求 | 响应 |
|---|---|---|
| `GET /api/clinics` | | 诊所数组（含停用） |
| `GET /api/clinics/{id}` | | 诊所 |
| `POST /api/clinics` | 诊所字段（不含 id、version） | 新建的诊所 |

诊所：

```json
{ "id":1, "name":"天河诊所", "postalAddress":"广州市天河区……", "managerName":"张主管",
```

### 9.3 UC09 维护牙医资料（总）

| 方法和路径 | 请求 | 响应 |
|---|---|---|
| `GET /api/dentists` | | 牙医数组（含停用，含资质） |
| `GET /api/dentists/{id}` | | 牙医 |

| `POST /api/qualifications` | `{ "name":"口腔种植" }` | 新建的资质；重名 → 409 `CONFLICT` |

牙医：

```json
{ "id":1, "employeeNo":"D001", "name":"林嘉文", "birthDate":"1985-03-12", "homeAddress":"……",

```

### 9.4 UC10 维护治疗项目与标准价格（总）

| 方法和路径 | 请求 | 响应 |
|---|---|---|
| `GET /api/treatment-items` | | 项目数组（含停用，含价格历史） |
| `GET /api/treatment-items/{id}` | | 项目 |
| `POST /api/treatment-items` | `{ "name","standardUnit","quantityScale","firstPrice":{ "effectiveFrom","unitPrice" } }` | 新建的项目 |
| `PUT /api/treatment-items/{id}` | `{ "name","standardUnit","quantityScale","active","version" }` | 更新后的项目 |

项目：

```json
{ "id":1, "name":"洁牙", "standardUnit":"次", "quantityScale":0, "active":true, "version":0,
  "currentPrice":120.00,
  "prices":[ { "id":1, "effectiveFrom":"2026-01-01", "unitPrice":120.00 } ] }
```

`prices` 按适用起始日期从早到晚排列。价格 ≥ 0；`quantityScale` 为 0—6；价格不提供修改和删除。新增价格成功后，项目的 `version` 加 1。

### 9.5 UC01 维护患者档案（前；医只读）

| 方法和路径 | 岗位 | 请求 | 响应 |
|---|---|---|---|
| `GET /api/patients?keyword=张&page=0&size=20` | 前、医 | `keyword` 模糊匹配姓名、电话或账号；不传则返回全部；`page` 从 0 开始，`size` 默认 20 | `{ "items":[患者摘要], "total":35 }` |
| `GET /api/patients/{id}` | 前、医 | | 患者 |
| `POST /api/patients` | 前 | 患者字段 + `confirmNotDuplicate`（布尔） | 新建的患者（含系统分配的 `accountNo`） |
| `PUT /api/patients/{id}` | 前 | 患者字段 + `version` | 更新后的患者 |

患者：

```json
{ "id":7, "accountNo":"P000007", "name":"张三", "birthDate":"1990-05-01", "billingAddress":"……",
  "phone":"13900000000", "email":null, "emergencyName":"李四", "emergencyPhone":"13900000001",
  "allergies":[ { "id":1, "name":"青霉素" } ], "allergyVerifiedAt":null, "version":0 }
```

患者摘要：`{ "id","accountNo","name","birthDate","phone" }`。

规则：
- 账号由后端分配，格式 `P` + 6 位数字，唯一。
- 新建时若存在“姓名相同且（出生日期相同或电话相同）”的患者，且请求里 `confirmNotDuplicate` 不为 `true`，返回 409 `CONFLICT`，`current` 放候选患者摘要数组；前端让用户核对后带 `confirmNotDuplicate: true` 重新提交。
- 请求里过敏用 `allergyIds` 数组。前台登记的过敏不设置核实时间；`allergyVerifiedAt` 只由牙医在 UC06 确认时写入。

### 9.6 UC02 安排就诊预约、UC03 取消、UC04 登记到诊（前；查询全）

| 方法和路径 | 岗位 | 请求 | 响应 |
|---|---|---|---|
| `GET /api/appointments?from=&to=&clinicId=&dentistId=&patientId=&status=` | 全（牙医只能查自己的） | 条件均可选；`from`、`to` 都不传时：有 `patientId` 则不限日期，否则为今天 | 预约数组，按预约时间从早到晚 |
| `GET /api/appointments/{id}` | 全 | | 预约 |
| `POST /api/appointments/check` | 前 | 同新建请求 | `{ "ok":true, "problems":[] }`，只检查不写库 |
| `POST /api/appointments` | 前 | `{ "patientId","dentistId","clinicId","scheduledAt","itemIds":[1,2],"requestId":null }` | 新建的预约 |
| `POST /api/appointments/{id}/cancel` | 前 | `{ "version":0 }` | 取消后的预约 |
| `POST /api/appointments/{id}/arrive` | 前 | `{ "arrivedAt":"2026-11-20T09:05:00", "dentistId":null, "clinicId":null, "version":0 }` | `{ "appointment":预约, "visitId":21 }` |

`status` 取第 7 节的预约状态值，可传多个（逗号分隔）。

预约：

```json
{ "id":1017, "status":"VALID", "scheduledAt":"2026-11-20T09:00:00",
  "patient":{ "id":7, "accountNo":"P000007", "name":"张三" },
  "dentist":{ "id":2, "employeeNo":"D002", "name":"周明远" },
  "clinic":{ "id":2, "name":"越秀诊所" },
  "items":[ { "id":1, "name":"洁牙" } ],
  "arrived":false, "cancelledAt":null, "cancelledBy":null, "visitId":null, "version":0 }
```

规则：
- 新建：患者、牙医、诊所必须存在且（牙医、诊所、项目）为启用状态；意向治疗至少一项；预约时间不能早于现在（按分钟比较：等于当前分钟可以，用于登记现场就诊）。这些不满足时返回 400 `INVALID_INPUT`，`fieldErrors` 的字段分别为 `patientId`、`dentistId`、`clinicId`、`itemIds`、`scheduledAt`。同一患者或同一牙医同一 `scheduledAt` 已有未取消预约 → 409 `CONFLICT`（`message` 写明是谁冲突，例如“周明远医生在该时间已有预约”“患者张伟在该时间已有预约”）。
- 由预约申请转入：`requestId` 可选，有值时该预约申请必须存在且为 `PENDING`（否则 409 `STATE_NOT_ALLOWED`“该预约申请已被处理”）；新建预约成功的同一事务里把预约申请改为 `CONFIRMED` 并关联这条预约（见第 9.17 节）。预约新建失败（如时间冲突）时预约申请保持不变。门店、时间可以和患者的期望不同。`check` 接口忽略 `requestId`。
- 检查（`check`）：把上面能查出的问题（含时间冲突）全部写进 `problems`（中文字符串数组），没有问题时 `ok` 为 `true`。
- 取消：已取消 → 返回原预约（200，不重复记录）；已到诊 → 409 `STATE_NOT_ALLOWED`。取消经办人填当前用户显示姓名。
- 到诊：建立唯一就诊并把到诊标记设为真，同一事务。`dentistId`、`clinicId` 为 `null` 时用预约上的；`arrivedAt` 不能晚于当前时间（400，字段 `arrivedAt`）；指定的牙医、诊所已停用 → 400，字段 `dentistId`、`clinicId`。已到诊 → 返回原结果（200）；已取消 → 409 `STATE_NOT_ALLOWED`。登记操作时间由后端取当前时间。


计价行：`{ "itemId":1, "itemName":"洁牙", "unitName":"次", "quantity":1, "unitPrice":120.00, "subtotal":120.00, "priceEffectiveFrom":"2026-01-01" }`。`priceEffectiveFrom`（所用价格的适用起始日期）只在 `price-lines` 的返回里有值，其他地方返回 `null`，因为已保存的治疗只存了单价快照。

确认请求：

```json
{ "problem":"牙龈出血", "specialNeeds":"无", "relatedHistory":null,
```

- 只有该就诊的接诊牙医能记录（`dentistId` 与当前用户绑定的牙医一致），否则 403。

- 未结算前可再次确认（更正或追加）；已结算或已按“未实施治疗”结束（`NO_TREATMENT`）→ 409 `STATE_NOT_ALLOWED`。
- 未实施治疗结束：仅 `UNCONFIRMED` 可用，原因必填，不产生治疗和结算单；状态变为 `NO_TREATMENT`。

- 季度未结束（`quarterEnded=false`）也可预览，但确认 → 409 `STATE_NOT_ALLOWED`。

- `quarter` 不在 1—4 → 400。

### 9.13 账号管理与修改密码（账号管理：总；修改密码：全）

| 方法和路径 | 岗位 | 请求 | 响应 |
|---|---|---|---|
| `GET /api/users` | 总 | | 账号数组，按 ID 排序（含停用） |
| `POST /api/users` | 总 | `{ "username","displayName","role","dentistId","password" }` | 新建的账号（201） |
| `PUT /api/users/{id}` | 总 | `{ "displayName","dentistId","active","version" }` | 更新后的账号 |
| `POST /api/users/{id}/reset-password` | 总 | `{ "newPassword":"……" }` | 账号（200） |
| `POST /api/auth/change-password` | 全 | `{ "oldPassword":"……","newPassword":"……" }` | `{ "ok":true }` |

账号：

```json
{ "id":2, "username":"dentist1", "displayName":"林嘉文", "role":"DENTIST",
  "dentist":{ "id":1, "employeeNo":"D001", "name":"林嘉文" }, "active":true, "version":0 }
```

`dentist` 只有牙医岗位有值，其他为 `null`。响应里永远不返回密码或哈希。

规则：
- 登录名 3—40 位，只能用字母、数字、下划线，唯一（重复 → 409 `CONFLICT`）；登录名和岗位创建后不能修改。
- 牙医岗位必须选择 `dentistId`，且该牙医未被其他账号绑定（已绑定 → 409 `CONFLICT`）；新开账号或改绑到另一位牙医时，这位牙医必须为启用状态（否则 400，字段 `dentistId`）；修改账号时保持原来绑定的牙医，即使该牙医已停用，也照常可以改显示姓名、停用或启用（牙医离职先停用牙医资料，再停用账号）。前台和总部岗位 `dentistId` 必须为 `null`（否则 400）。
- 密码 6—64 个字符，且 UTF-8 编码不超过 72 个字节（BCrypt 的上限），超过 → 400“密码太长（最多 72 个字节，约 24 个汉字）”，字段为 `password` 或 `newPassword`；新建、重置、修改都用 BCrypt 保存。
- 停用账号或重置密码时，该账号已登录的令牌全部作废；总部不能停用自己（409 `STATE_NOT_ALLOWED`）。被停用的账号登录返回 401“账号已停用，请联系总部”。
- 修改密码：原密码错误 → 400，`fieldErrors` 为 `oldPassword`；新密码与原密码相同 → 400，字段 `newPassword`。成功后作废该账号的**其他**令牌，当前令牌继续有效。
- 账号新建、修改、停用、重置密码、修改密码都写操作记录（详情里不记录密码）。

### 9.14 操作记录查询（总）

`GET /api/operation-logs?from=2026-11-01&to=2026-11-21&userId=&action=&targetType=&keyword=&page=0&size=20`

```json
{ "items":[ { "id":31, "occurredAt":"2026-11-21T09:05:12", "userId":1, "username":"front1", "displayName":"王丽",
              "action":"REGISTER_ARRIVAL", "targetType":"APPOINTMENT", "targetId":1017, "detail":{ …原样的 JSON… } } ],
  "total":35 }
```

规则：
- `from`、`to` 按操作日期（两端包含），都不传时为最近 7 天；`from` 晚于 `to` → 400。`page` 从 0 开始，`size` 默认 20、最大 100。按操作时间从近到远。
- `action`、`targetType` 精确匹配；`keyword` 匹配登录名、显示姓名或对象 ID。
- `targetType` 输出统一为大写：`CLINIC`、`DENTIST`、`QUALIFICATION`、`TREATMENT_ITEM`、`PATIENT`、`APPOINTMENT`、`VISIT`、`SETTLEMENT`、`QUARTER_CLOSE`、`USER`、`APPOINTMENT_REQUEST`。
- `action` 取值：`CREATE`、`UPDATE`、`ADD_STANDARD_PRICE`、`CREATE_APPOINTMENT`、`CANCEL_APPOINTMENT`、`REGISTER_ARRIVAL`、`CONFIRM_VISIT`、`END_WITHOUT_TREATMENT`、`ISSUE_SETTLEMENT`、`CONFIRM_QUARTER`、`CREATE_USER`、`UPDATE_USER`、`RESET_PASSWORD`、`CHANGE_PASSWORD`、`CONFIRM_APPOINTMENT_REQUEST`、`INVALIDATE_APPOINTMENT_REQUEST`。
- `detail` 是写入时保存的 JSON，原样解析成对象返回（不能解析时返回字符串）；`displayName` 取当前账号的显示姓名。
- 只读，不写操作记录。

### 9.16 患者注册与登录（患者端）

| 方法和路径 | 岗位 | 请求 | 响应 |
|---|---|---|---|
| `POST /api/patient-auth/sms-code` | 免登录 | `{ "phone":"13900000001", "purpose":"REGISTER" }` | `{ "sent":true, "message":"课程演示：验证码统一为 123456" }` |
| `POST /api/patient-auth/register` | 免登录 | `{ "phone","code","name","password" }` | `{ "token","expiresAt","patient":患者账号 }`（201） |
| `POST /api/patient-auth/login` | 免登录 | `{ "phone","password" }` | `{ "token","expiresAt","patient":患者账号 }` |
| `POST /api/patient-auth/reset-password` | 免登录 | `{ "phone","code","newPassword" }` | `{ "ok":true }` |
| `GET /api/patient-auth/me` | 患 | | 患者账号 |
| `POST /api/patient-auth/logout` | 患 | | 200 |

患者账号：

```json
{ "id":1, "phone":"13900000001", "name":"张伟", "createdAt":"2026-11-20T10:00:00" }
```

规则：
- **验证码**：课程系统不接短信服务，验证码统一为 `123456`。`sms-code` 只检查手机号并返回上面的提示，不真的发送；`register`、`reset-password` 的 `code` 不是 `123456` → 400，字段 `code`，“验证码不正确”。`purpose` 取 `REGISTER`（注册）或 `RESET_PASSWORD`（找回密码）。
- 手机号必须是 11 位、以 1 开头的数字（`^1\d{10}$`），否则 400，字段 `phone`。
- 注册：手机号已注册 → 409 `CONFLICT`“该手机号已注册，请直接登录”（`sms-code` 的 `REGISTER` 也同样检查）；姓名 1—20 个字符（400，字段 `name`）；密码规则同第 9.13 节（字段 `password`），BCrypt 保存。注册成功即登录，返回令牌。
- 登录：手机号未注册或密码错误一律 401“手机号或密码不正确”。
- 找回密码：手机号未注册 → 404“该手机号尚未注册”（`sms-code` 的 `RESET_PASSWORD` 也同样检查）；密码规则同上（字段 `newPassword`）；成功后作废该账号全部令牌。
- 患者令牌有效期 **7 天**；退出立即作废本次令牌。
- 患者账号**不是**患者档案（第 9.5 节），两者不关联：患者账号只能管理自己的预约申请，看不到病历、就诊和结算单。
- 响应里永远不返回密码或哈希；注册、找回密码不写操作记录（操作记录只记员工操作）。

### 9.17 预约申请（患者提交、撤回；前台处理）

| 方法和路径 | 岗位 | 请求 | 响应 |
|---|---|---|---|
| `GET /api/patient/appointment-requests` | 患 | | 本人的预约申请数组，按提交时间从近到远 |
| `POST /api/patient/appointment-requests` | 患 | `{ "clinicId":1, "preferredDate":"2026-11-25", "timeSlot":"MORNING", "itemIds":[1,2], "note":"" }` | 新建的预约申请（201） |
| `POST /api/patient/appointment-requests/{id}/withdraw` | 患 | `{}` | 撤回后的预约申请 |
| `GET /api/appointment-requests?status=&clinicId=&from=&to=` | 前 | 条件均可选；`from`、`to` 按提交日期，都不传时为最近 30 天；`status` 可传多个（逗号分隔） | 预约申请数组，按提交时间从近到远 |
| `GET /api/appointment-requests/{id}` | 前 | | 预约申请 |
| `POST /api/appointment-requests/{id}/invalidate` | 前 | `{ "reason":"多次致电无人接听", "version":0 }` | 处理后的预约申请 |

转为正式预约不单独设接口：前台用 `POST /api/appointments` 并带 `requestId`（第 9.6 节）。

预约申请：

```json
{ "id":5, "status":"PENDING", "createdAt":"2026-11-21T20:15:00",
  "contactName":"张伟", "contactPhone":"13900000001",
  "clinic":{ "id":1, "name":"天河诊所", "phone":"020-38880001" },
  "preferredDate":"2026-11-25", "timeSlot":"MORNING",
  "items":[ { "id":1, "name":"口腔检查" } ], "note":"牙齿遇冷敏感",
  "handledAt":null, "handledBy":null, "invalidReason":null, "withdrawnAt":null,
  "appointment":null, "version":0 }
```

`appointment` 在 `CONFIRMED` 时有值：`{ "id":1031, "status":"VALID", "scheduledAt":"2026-11-25T09:30:00", "dentist":{ "id":1, "name":"林嘉文" }, "clinic":{ "id":1, "name":"天河诊所" } }`，其中 `status` 是这条预约**当前**的状态（第 7 节），预约后来被取消时显示 `CANCELLED`。`handledBy` 为处理人的显示姓名。

规则：
- 提交：`contactName`、`contactPhone` 取自患者账号并随记录保存。门店须存在且启用（400，字段 `clinicId`）；`preferredDate` 须在今天到今天后 30 天之间（400，字段 `preferredDate`）；`timeSlot` 取第 7 节的值（400，字段 `timeSlot`）；`itemIds` 可以为空，有值时每项须存在且启用（400，字段 `itemIds`）；`note` 最多 200 字（400，字段 `note`）。同一患者账号最多 3 条 `PENDING` → 409 `STATE_NOT_ALLOWED`“您已有 3 条待确认的预约，请等待前台联系或撤回后再提交”。
- 患者只能看到、撤回自己的预约申请；别人的返回 404。
- 撤回：`PENDING` → `WITHDRAWN`，记录 `withdrawnAt`；已撤回 → 返回原记录（200）；`CONFIRMED`、`INVALID` → 409 `STATE_NOT_ALLOWED`“前台已处理，如需取消请致电门店”。
- 判定无效：只有 `PENDING` 可以（否则 409 `STATE_NOT_ALLOWED`）；`reason` 1—200 字必填（400，字段 `reason`）；带 `version`，不一致 → 409 `CHANGED`；记录 `handledAt`、`handledBy`。
- 转为预约见第 9.6 节；同一事务写 `handledAt`、`handledBy`、关联预约。
- 操作记录：转为预约时，除 `CREATE_APPOINTMENT`（`detail` 中带 `requestId`）外，另写一条 `CONFIRM_APPOINTMENT_REQUEST`；判定无效写 `INVALIDATE_APPOINTMENT_REQUEST`。两者对象类型为 `APPOINTMENT_REQUEST`，`detail` 为 `{ "before":…, "after":… }`。患者提交、撤回不写操作记录（记录本身保存了提交和撤回时间）。
